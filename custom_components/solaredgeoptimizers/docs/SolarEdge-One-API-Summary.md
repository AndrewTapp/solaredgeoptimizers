# SolarEdge One API

## Upgrading from an earlier version

If you are on a version prior to v2.4.0 (or want a clean registry after any upgrade), the steps below ensure entities and devices are recreated correctly:

1. **Update the integration via HACS** so the new code (including cleanup) is installed.
2. **Restart Home Assistant** (optional but recommended).
3. **Remove the integration from Home Assistant:** **Settings → Devices & services → Integrations** → SolarEdge Optimizers → **Delete**. This runs `async_remove_entry` and cleans entity and device registries for that entry.
4. **Restart Home Assistant** (optional but recommended).
5. **Clear browser cache** [Ctrl]+[Shift]+r on Microsoft Edge.
6. **Re-add the integration** with the same Site ID, username, password, and options. You get fresh entities and a clean registry; history reconnects because `unique_id`s are the same.

## What it is

SolarEdge One is SolarEdge’s newer monitoring portal and API. It replaces the older “legacy” monitoring portal and its ad-hoc endpoints with a structured, service-oriented API under `monitoring.solaredge.com/services/...`.

## Dual API: One first, legacy fallback

When **Use SolarEdge One** is **on** (default), the integration tries SolarEdge One first. If One returns no valid measurements (e.g. "Missing or invalid measurements" for all optimizers) or One login fails, it **automatically falls back** to the legacy SolarEdge API. When data is currently from the legacy API, the integration **forces a full refresh every 30 minutes** so it re-tries SolarEdge One and can switch back when One is available again. When **Use SolarEdge One** is **off**, the integration stays on the legacy API only.

A site-level sensor **Obtained from** shows whether current data came from **"One API"** or **"Legacy API"**. The legacy API can have delayed readings (an hour or more); when One works, it generally provides more timely data.

## How it replaces the old API

- **Same purpose**: Both APIs expose site layout (inverters → strings → optimizers), live per-optimizer data (power, voltage, current, optimizer voltage), and lifetime energy. The integration presents the same hierarchy and sensors either way.

- **Different tech**:
  - **Legacy**: Basic Auth + web session (cookies/CSRF), separate endpoints for layout, per-panel `systemData`, and layout/energy. Data is scraped from web-style URLs and responses. If SolarEdge stops issuing `CSRF-TOKEN` from `/solaredge-web/p/login`, the integration retries `/solaredge-web/p/logout/slo` and then `/solaredge-web/p/login` before CSRF-protected POSTs. If SolarEdge still rejects the legacy POST flow, the logs now call out **HTTP 498** explicitly as a likely CSRF / legacy-session rejection.
  - **SolarEdge One**: OAuth/OIDC (PKCE) via `login.solaredge.com`; access token is then used as Bearer on all `/services/` calls. Layout comes from a single v2 layout endpoint; optimizer live + basic info from a POST to `/layout/information/optimizers`; lifetime energy from the energy-graph API. Cleaner, REST-style design.

- **Same credentials**: Site ID, username, and password are unchanged; the integration uses them for both One and legacy and chooses which backend to use automatically at each refresh.

## Benefits of SolarEdge One (for the integration)

- **Auth**: Single OAuth flow and Bearer token instead of mixing Basic Auth and session cookies.
- **Data**: Structured JSON (e.g. `power_W`, `voltage_V`, `optimizerVoltage_V`) instead of locale-dependent labels; layout in a single v2 structure.
- **Devices**: Optimizer and inverter **model** (and serial) come from the API, so HA devices can show real model names (e.g. P405-4RM4MRM-NA25, SE5000H-RW000BNN4). When the API provides a **panel type** (description, e.g. SunPower SPR-MAX3-400), it is included in the optimizer device model and exposed as a **panel_type** attribute on optimizer sensors.
- **Polling**: Lightweight “any new data?” check can use a batch request (up to `LIGHT_CHECK_BATCH_SIZE` = 5 optimizers) instead of one panel; 1-hour stale threshold for live values (legacy uses 2 hours). Site layout (panels) is cached for **2 hours** (`PANELS_CACHE_TTL_ONE`) when using SolarEdge One. **Full refresh** fetches all optimizer live data in **one batch POST** (`requestSystemDataBatch` with all serials), reducing portal load; if that batch fails (e.g. 5xx), the integration falls back to per-optimizer requests.

## In this integration

- A **dual API** wrapper (`api_dual.py`) tries SolarEdge One first when **Use SolarEdge One** is enabled; if One has no valid measurements or fails, it uses the legacy API. When **Use SolarEdge One** is disabled, the wrapper uses the legacy API only.
- Both backends implement the same `SolarEdgeAPIProtocol` and feed the same coordinator and sensor layer, so behaviour (sensors, hierarchy, aggregation) is the same; only the API client (legacy vs `solaredge_one_api`) and the exact endpoints/auth differ. The **Obtained from** sensor on the site device shows which source provided the current data.
- **Entity IDs (optimizer sensors):** The sensor platform sets `has_entity_name=False` for per-optimizer entities so `entity_id` uses the full path-based `suggested_object_id` (e.g. `sensor.power_1_1_1`) without Home Assistant prepending the optimizer device slug. Friendly names use the short translated sensor label only (e.g. “Power”); the optimizer device shows position. This applies the same whether the active backend is One or legacy.
- **Device hierarchy (v2.4.17+):** The coordinator registers site, inverter, and string devices before entities are added. Entities link with identifiers-only `device_info` (`device_ids.link_device_info`) so Home Assistant does not re-validate `via_device` during `async_add_entities` (avoids startup warnings). Device names in the UI still come from the device registry entries created by the coordinator.
- **Large-site startup (v2.4.18+):** The sensor platform registers entities in batches (`ENTITY_ADD_BATCH_SIZE`) with event-loop yields; this is independent of the One API but reduces registry/websocket load when many optimizer sensors are created.
- **Temperature sensor updates (SolarEdge One):** The temperature value is the optimizer's **maximum daily temperature** from the by-inverter endpoint. When the coordinator does not perform a full refresh (e.g. it reuses existing data after a lightweight check), it still refreshes optimizer maximum daily temperatures when the temperature cache expires (**30 minutes**, `TEMPERATURE_CACHE_TTL`) via `get_optimizer_temperatures_cached()` (layout/energy by-inverter with `include-max-temperature`). So temperature sensors stay up to date even when power, voltage, and current are not being refreshed. The coordinator calls `_refresh_temperature_when_no_full_refresh()` for this. The portal may report temperature in °C or °F (`temperatureUnit`); the integration converts Fahrenheit to Celsius for storage so values are correct for all regions (e.g. US users). Debug logging logs per-optimizer F→°C conversion and a summary count when Fahrenheit is detected.
- **Lifetime energy (SolarEdge One):** Per-optimizer lifetime energy comes from the energy-graph API (one GET per optimizer, 1-hour cache). When the cache is cold, `get_lifetime_energy_cached()` fetches these requests **in parallel** (thread pool, up to `MAX_PARALLEL_WORKERS` = 10 concurrent requests) inside a `with ThreadPoolExecutor(...)` block so workers shut down cleanly. **Site** lifetime can use the portal's dashboard production (Wh) from `get_dashboard_site_production_cached(installation_date)` when it is greater than the aggregated total; **inverter** and **string** can use the portal's layout/energy by-inverter (Wh) from `get_layout_energy_by_inverter_cached(installation_date)` when greater than their aggregated totals. The **coordinator** maps by-inverter **string** buckets to layout strings by sorting **relativeOrder** and portal keys (not list index alone) and **skips** a string-level portal override when portal Wh exceeds the optimizer-sum aggregate by more than **STRING_LIFETIME_PORTAL_OVERRIDE_MAX_RATIO** (default 3×, `const.py`)—some sites return a bad per-string bucket. The start date for these portal calls is the site **installation date** from site info (`get_site_info_cached()` → layout/information/site). Site info (installation date, peak power in kW) is cached per `SITE_INFO_CACHE_TTL` (2 h) and powers the site-level **Installation date** and **Peak power** sensors.
- **Connections / file descriptors:** Routine One API calls use `requests.get`/`post` with a response context manager. OAuth uses a short-lived `Session()` inside `with`. Parallel energy fetches use `ThreadPoolExecutor` as a context manager. `close()` on the One client clears tokens; the dual API `close()` also closes the legacy client’s tracked sessions. In the legacy client, failed session bootstrap closes the temporary `Session` immediately rather than leaving a half-initialized session around.
- **Aggregated last measurement:** At string/inverter/site, the integration uses the latest timestamp among **active** optimizers / strings / inverters respectively; unknown when none qualify (no substitution with “now”).
- **Optimizer requests:** Full refresh uses **one batch POST** to `/layout/information/optimizers` with all optimizer serials in the body (same endpoint as the light check, which sends up to 5 serials). This reduces portal calls from N to 1 per full refresh. POSTs use `API_TIMEOUT_LONG` (60s) timeout and **one automatic retry** on read/connect timeout to reduce failures when the portal is slow. If the batch fails (e.g. 5xx), the integration falls back to per-optimizer requests. The response can include a **description** (panel type, e.g. SunPower SPR-MAX3-400) in `basicInformationList` or `serialToLiveData`; when present, the integration uses it for the optimizer device model and the **panel_type** sensor attribute.
- **Last measurement for inactive optimizers:** For inactive optimizers the API often omits `lastMeasurement`. The integration does not default to the current time; it preserves the previous last measurement across refreshes so the **Last measurement** sensor shows when the optimizer was actually last updated (or unknown on first load before any previous data).
- **Inverter information:** If the inverter information API returns **403 Forbidden** (e.g. some accounts lack that permission), the integration still works: inverter and optimizer devices use position- or display-name-based identity (at string/optimizer level, names and entity IDs follow the API display name when it parses, e.g. "1.0", "1.0.1"), so model names may be missing but all sensors and devices function. A one-time warning is logged.
- **Status sensors:** Optimizer, string, and inverter status sensors show the device status from the API. **Blank** (empty) status is treated as active and displayed as **blank** with the active icon. The icon changes dynamically: check-circle for Active or blank, alert-circle for Inactive, help-circle for unknown (any other) status. This makes it easy to spot inactive devices at a glance in the Home Assistant UI.
- **Azimuth and Tilt sensors:** Optimizer azimuth and tilt sensors show the panel orientation from the API (when available). Azimuth uses a compass icon; Tilt uses an angle-acute icon.
- **Site-level Installation date and Peak power:** The integration fetches site information from `.../services/layout/information/site/{siteId}` (cached 2 h). This provides **installation date** (for the site-level Installation date sensor and as the start date for portal lifetime energy calls) and **peak power** in kW (for the site-level Peak power sensor). These sensors appear only when using the SolarEdge One API.
- **Inverter-level Max active power:** The site layout (`.../services/layout/logical/generic/v2/site/{siteId}?include-optimizers=true`) returns per-inverter `maxActivePower` in watts. The integration converts to kW and exposes a **Max active power** sensor on each inverter device. Same cache as the layout (2 h). Only available when using the SolarEdge One API.
